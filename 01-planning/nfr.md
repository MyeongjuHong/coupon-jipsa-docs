# 비기능 요구사항 명세서

> 프로젝트 특성(가족/지인용, 모바일 웹, 소규모)을 고려한 현실적 목표 설정

---

## 1. 성능(Performance)

| 항목             | 목표/기준                                   | 선택 이유                                                                          |
| ---------------- | ------------------------------------------- | ---------------------------------------------------------------------------------- |
| 페이지 응답 시간 | 1초 이내                                    | 가족이 원하는 쾌적한 속도. 2초도 괜찮지만 저장된 이미지 로딩 감안 시 1초 목표 필요 |
| API 응답 시간    | 500ms 이내                                  | 10명 규모 소규모 데이터라 충분. 더 빠르면 좋지만 개발 복잡도 대비 효율 낮음        |
| 동시 접속자 처리 | v0.1: 10명, v0.2: 50명, 이후: 필요시 스케일 | 초기엔 가족 중심, 점진적 확대. 무료 호스팅(Cloudflare Pages, Fly.io) 기준 설정     |

---

## 2. 가용성(Availability)

| 항목                       | 목표/기준               | 선택 이유                                                                |
| -------------------------- | ----------------------- | ------------------------------------------------------------------------ |
| 목표 가동률(SLA)           | 설정 안 함              | 개인 프로젝트라 24/7 모니터링 불가. 대신 빠른 복구에 집중                |
| 허용 다운타임              | 수동 개입 시 1시간 이내 | 금융성 아이템 다루므로 단순 방치 불가, 하지만 대기업 수준(15분)은 불필요 |
| 장애 복구 목표 시간(RTO)   | 1시간 이내              | 위와 동일                                                                |
| 데이터 손실 허용 범위(RPO) | 1시간 이내              | Supabase 자동 백업 주기 기준. 하루 이상 손실 없음                        |

---

## 3. 확장성(Scalability)

| 항목             | 목표/기준                                                                    | 선택 이유                                                                                      |
| ---------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 예상 사용자 증가 | v0.1: 10명 → v0.2: 100명 → v2.0(앱): 1000명                                  | 단계적 성장 가정. 각 버전마다 재평가 필요                                                      |
| 스케일 아웃 전략 | Cloudflare Pages(프론트) / Fly.io(백엔드) 자동 스케일링 + Supabase 용량 증설 | 초기 무료 호스팅 최대 활용, 사용자 증가 시 유료 전환. Docker는 백엔드 개발자 협업 시 추가 고려 |

---

## 4. 보안(Security)

| 항목               | 목표/기준                                        | 선택 이유                                                                          |
| ------------------ | ------------------------------------------------ | ---------------------------------------------------------------------------------- |
| 인증 방식          | 카카오 OAuth 단일 인증                           | 1인 1계정 보장(사업자등록 없음) + 비밀번호 관리 부담 제거. DEC-4 참조              |
| 데이터 암호화      | AES-256 (저장), TLS (전송)                       | 기프티콘 코드는 금융성 아이템이므로 최고 수준 암호화 필수. RSA는 느리고 DES는 약함 |
| 접근 권한 관리     | 스페이스 기반 멤버십 제어                        | 초대 승인 시스템으로 비멤버 접근 차단. DEC-3 참조                                  |
| 개인정보 보호 준수 | 개인정보보호법 준수 (동의 후 보관, 30일 후 삭제) | 카카오 이메일/이름은 최소 필요 정보만 저장. DEC-5 참조                             |
| 취약점 점검 주기   | 필요시 + Sentry 자동 감지                        | 1인 개발이라 주기적 점검 어려움. Sentry가 자동으로 에러 추적하므로 충분            |

---

## 5. 사용성(Usability)

| 항목                   | 목표/기준                                            | 선택 이유                                                                          |
| ---------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 접근성                 | 모바일 기본 접근성 (버튼 크기, 폰트 조절, 색상 대비) | 비개발자 가족도 쉽게 사용 필요. WCAG 완전 준수는 법적 의무 아니므로 v1.0 이후 고려 |
| 지원 언어              | 한글 (v0.1)                                          | 국내 사용자 우선. 영어는 앱 출시(v2.0) 시 필요 시 추가                             |
| 지원 디바이스/브라우저 | iOS Safari 12+, Android Chrome 8+ (모바일 우선)      | 가족 구성원 기준. 데스크톱은 반응형 지원하되 최적화 우선순위 낮음                  |

---

## 6. 유지보수성(Maintainability)

| 항목           | 목표/기준                                         | 선택 이유                                                         |
| -------------- | ------------------------------------------------- | ----------------------------------------------------------------- |
| 코드/설계 표준 | ESLint + Prettier + TypeScript                    | 자동 포매팅 + 타입 안전성으로 일관성 유지.                        |
| 문서화 범위    | 기획 문서(SRS, 유스케이스) + API 명세 + 개발 노트 | 회고/면접 준비용. 모든 결정사항 추적 필요                         |
| 배포 방식      | GitHub Actions (CI/CD 자동화)                     | 수동 배포 시간 절약 + 배포 실패 방지. Docker는 협업 단계에서 추가 |

---

## 7. 호환성(Compatibility)

| 항목     | 목표/기준                             | 선택 이유                                                                      |
| -------- | ------------------------------------- | ------------------------------------------------------------------------------ |
| OS       | iOS 12+, Android 8+                   | 가족 폰 대부분이 이 정도 버전. 앱 출시 시 재평가                               |
| 브라우저 | Chrome, Safari, Firefox (모바일 중심) | 점유율 상위 3개. 데스크톱은 보조                                               |
| 디바이스 | 모바일 웹 우선 (태블릿/PC는 반응형만) | 사용 맥락이 "알림 후 즉시 접속"이므로 모바일 필수. 데스크톱 최적화는 v1.0 이후 |

---

## 8. 모니터링 및 로깅

| 항목           | 목표/기준                | 선택 이유                                                     |
| -------------- | ------------------------ | ------------------------------------------------------------- |
| 로그 보관 기간 | 1개월 (Sentry 무료 티어) | 최근 에러만 추적하면 충분. 용량 부족 시 유료 전환             |
| 모니터링 도구  | Sentry                   | 에러 추적 + 성능 모니터링 무료 제공. 대체제(DataDog)는 유료   |
| 알림 기준      | 에러 발생 시 즉시 이메일 | 금융성 아이템 다루므로 빠른 대응 필수. 알림 폭주 시 설정 조정 |

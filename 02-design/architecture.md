## 3. 배포 아키텍처

| 컴포넌트         | 배포 환경        | 선택 이유                                           | 트레이드오프                                                                     | 비고                                                                                             |
| ---------------- | ---------------- | --------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **프론트**       | Cloudflare Pages | 무료 티어에 Vercel은 안되는 상업적 이용까지 가능    | Next.js 돌리려면 `next-on-pages` 어댑터 필요, Vercel 대비 Next.js 특화 기능 제한 | 트래픽 증가 시 Vercel Pro 재검토                                                                 |
| **백엔드**       | Render           | 무료티어 존재, 자동 배포 지원                       | 콜드스타트 있어 cron 필요, 동시 요청 몰리면 응답 지연 (512 RAM, 공유 CPU 제한)   | 실사용자 확보 후 Fly.io 마이그레이션 검토                                                        |
| **데이터베이스** | Supabase         | 무료티어 존재, 스토리지와 동일한 계정으로 관리 가능 | 7일 미사용 시 자동 일시정지, RDS 대비 리전 선택지 적음                           | Render 헬스체크 cron에 Supabase 쿼리 포함 (주 2회), 무료티어 사용으로 중요 데이터 별도 수동 백업 |
| **스토리지**     | Supabase Storage | 무료티어 존재, DB와 같은 계정으로 관리 가능         | S3 대비 성숙도/안정성 낮고 세밀한 IAM 제어 약함                                  | 이미지 용량 증가시 AWS S3 마이그레이션 검토                                                      |

### 배포 흐름

```markdown
GitHub Push (main 브랜치)
↓
프론트: Cloudflare Pages가 push 감지 -> 자동 빌드(next build) -> 자동 배포
백엔드: Render가 push 감지 -> 자동 빌드(npm install, build) -> 자동 배포
↓
프로덕션 배포

> 별도 CI/CD 파이프라인(GitHub Actions 등)은 v0.1에서 불필요
> 두 플랫폼 모두 Git push 기반 자동 배포를 기본 제공
> 테스트 자동화(v0.2, Vitest 도입) 이후 '빌드 전 테스트 실행' 단계 추가 검토
```

## 4. 보안 설계

### 인증/인가 (DEC-4 참고)

| 항목          | 구현 방식                                                                                                                     | 선택 이유                                                                                                                                                                       | 비고                                                                                                                                                |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **인증**      | JWT로 토큰 기반 인증                                                                                                          | 서버가 로그인 상태를 별도로 저장할 필요X(stateless) → 무료 서버(Render)가 재시작(콜드스타트)돼도 로그인 유지 가능                                                               | -                                                                                                                                                   |
| **토큰 저장** | Access Token(1시간)과 Refresh Token(2주) 모두 HTTPOnly 쿠키에 저장, Refresh Token으로 Sliding Sessioin(자동 로그인 연장) 구현 | localStorage는 XSS 공격 시 JS로 토큰이 그대로 탈취될 수 있으나, HttpOnly 쿠키는 JS 접근 자체가 불가능해 더 안전, 브라우저가 요청마다 자동으로 쿠키 전송해 별도 헤더 관리 불필요 | CORS 설정시 `credentials: ‘include’` 명시 필요, v2.0 모바일 앱은 브라우저가 아니므로 쿠키 방식이 통하지 않아 별도 인증 방식(헤더 토큰) 추가 검토 필요 |
| **권한 제어** | 스페이스 멤버십 기반 접근 제어: 그룹 스페이스에 속하지 않는 사용자는 해당 스페이스의 쿠폰에 접근 불가 (DEC-3)                 | 인증(누구인지)과 별개로 `이 데이터에 접근해도 되는지` 판단하는 인가(Authorization) 로직 필요                                                                                    | -                                                                                                                                                   |

### 데이터 암호화 (DEC-4, NFR 참고)

| 항목         | 구현 방식                                                                                              | 선택 이유                                                                                                                                                                                                       | 비고                             |
| ------------ | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| **저장 시**  | AES-256                                                                                                | 대칭키 암호화 중 가장 널리 검증된 표준 (금융/군사 기관 채택), 256비트 키 길이로 현재 컴퓨팅 기술로는 브루트포스가 사실상 불가능. RSA는 비대칭 방식이라 대용량 데이터 암호화에 느리고, DES는 키 길이가 짧아 취약 | 기프티콘 코드 등 민감정보에 적용 |
| **전송 시**  | TLS (HTTPS)                                                                                            | 클라이언트-서버 간 통신 구간을 암호화하는 업계 표준. Cloudflare/Render 모두 기본 제공하여 별도 설정 불필요                                                                                                      | -                                |
| **민감정보** | 기프티콘 코드는 DB에 AES-256으로 암호화 저장, Sentry 등 로그에는 마스킹 처리하여 원본이 남지 않도록 함 | 에러 로그에 원본 코드가 그대로 노출되면 DB 암호화 자체가 무의미해짐                                                                                                                                             | -                                |

## 7. 주요 결정사항 및 트레이드오프 요약

| 결정             | 선택한 방식                          | 주요 이유                                                                                                                  | 포기한 대안                                                                                                  |
| ---------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **프레임워크**   | Next.js                              | 파일 기반 라우팅과 API Route 통합으로 1인 개발 속도 향상, 채용 시장 표준                                                   | Vite + React(SPA) - 이 서비스는 로그인 후 사용이라 SEO 필요성은 낮지만, 생태계/채용 시장 고려해 Next.js 유지 |
| **백엔드**       | NestJS                               | 채용 시장에서 Express 대비 선호도 상승 추세라 취업 준비 목적, 모듈 구조로 확장성 확보                                      | Express/Fastify - 소규모 프로젝트엔 더 가볍지만 학습 목적상 NestJS 선택                                      |
| **데이터베이스** | Prisma + PostgreSQL                  | 학습 자료가 많아 1인 개발에 적합, Supabase가 PosgreSQL만 지원해 사실상 결정                                                | Drizzle - 더 가볍고 인기 상승 중이나 생태계 성숙도에서 Prisma가 유리                                         |
| **배포**         | Cloudflare Pages + Render + Supabase | 모두 무료 티어 제공, Cloudflare는 상업적 이용 제한 없음, Supabase는 DB/인증/스토리지 통합 관리로 1인 개발 설정 비용 최소화 | Vercel(상업 이용 제한) / AWS(RDS+S3, 설정 비용 큼)                                                           |
| **인증**         | Kakao OAuth                          | 한국 사용자 대상 서비스에 최적, 비밀번호를 직접 저장하지 않아 유출 리스크 감소                                             | 자체 화원가입(이메일/비밀번호) - 비밀번호 관리 부담과 유출 리스크로 제외                                     |
